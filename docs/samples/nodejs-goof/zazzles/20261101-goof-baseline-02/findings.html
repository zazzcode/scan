Scope & limitations

  • ESM named relative imports and direct returned handler factories only; no re-exports or CommonJS resolution
  • ESM Express receiver construction and direct registrations required; chained routes, mount composition and effective middleware are not resolved
  • Supported helper calls bind identifier parameters and direct returns; branches, closures, wrappers, unknown calls, recursion, and asynchronous response continuations remain uncertain
  • SQL text, NoSQL $where strings, query documents, and request-field validation are candidate findings, not confirmed vulnerabilities
Finding-type glossary · 8 definitions

Types identify security review areas. A type name does not establish vulnerability or detector coverage; always read the result status.

SQL Injection

Coverage: bounded analysis

Input changes executable SQL structure instead of remaining a data value, potentially changing what the database reads or writes.

How to interpret this type

An SQL Injection pill identifies the risk family being reviewed. String-built executable SQL is poor practice to remediate even without a proven exploit; a library-managed search value may remain unresolved. The finding status and evidence determine the actual claim. The pill alone does not confirm injection.

Remediation approach

Use the verified driver's parameter-binding API for values. Review dynamic identifiers separately. Keep business-field validation independent of query-structure protection.

NoSQL Injection

Coverage: bounded analysis

Untrusted input changes a NoSQL query's operators, selector structure, or executable expression rather than remaining an allowed data value.

How to interpret this type

Executable $where string construction is poor practice to refactor even without a proven exploit. An unmodeled document constraint alone is Review, not an established defect. Inspect actual value types, keys, transformations, library behavior, and the named status.

Remediation approach

Prefer data-only query APIs, constrain scalar slots and permitted keys/operators, and avoid building executable $where strings from input.

Input Validation

Coverage: bounded analysis

Server-side checks enforce the business requirements for a field, such as required presence, runtime type, permitted format, range, or length.

How to interpret this type

Poor input validation means an applicable requirement is not adequately enforced. This neutral family label also covers unresolved checks and supported protection: no validator identified in an analyzed slice is not proof that every execution path lacks validation. Free-text punctuation is not itself a defect.

Remediation approach

Define field-specific requirements and enforce them before use on all applicable paths. Verify guard behavior and middleware. Apply destination-specific protection separately.

Account Creation Validation

Coverage: bounded analysis

Required account fields and enforcing guards must be checked before an account is persisted.

How to interpret this type

Review field requirements, conditional bypasses, and generated persistence behavior. A modeled create operation alone does not prove a registration bypass.

Remediation approach

Enforce required fields before persistence, terminate rejected paths, add appropriate database constraints, and test the persisted result.

Outbound Request Safety

Coverage: bounded analysis

Input used in an outbound request may affect its destination, headers, or other request values. Unrestricted destination control can lead to server-side request forgery (SSRF).

How to interpret this type

The current scanner records bounded outbound-use evidence. A pill does not establish SSRF, destination reachability, or complete response-flow analysis.

Remediation approach

Verify allowed destinations and protocols, redirect handling, network boundaries, and sensitive request values for the specific HTTP client.

Reflected XSS

Coverage: planned

Request-controlled content is reflected into a browser response in a context that allows it to execute as script.

How to interpret this type

XSS means cross-site scripting. This glossary entry is vocabulary for a planned detector; the current reporting increment does not detect or assign Reflected XSS findings.

Remediation approach

Use context-appropriate output encoding and safe template or DOM APIs. Input validation alone does not replace correct output handling.

Sensitive Data Logging

Coverage: bounded analysis

Logs expose credentials, tokens, personal information, or other sensitive values to readers or storage that should not receive them.

How to interpret this type

Covers verified console and winston calls in analyzed route handlers that receive request values with credential or personal-data evidence. A field name is a hint for review, not proof; Authorization and Cookie headers are credentials by HTTP semantics. Morgan request logging that records URLs is checked against credentials read from the query string. Constant messages are not leaks. Non-request secrets and logger redaction configuration are not yet analyzed.

Remediation approach

Avoid logging secrets; minimize sensitive fields and apply verified redaction before emission. Review log access and retention.

Sensitive Operation Review

Coverage: bounded analysis

A possible sensitive use was recorded but does not yet map to a more specific supported risk family.

How to interpret this type

This is an analysis category. Inspect the evidence and missing operation semantics before making a security claim.

Remediation approach

Resolve the source, operation, API behavior, and required protection before selecting a fix.
